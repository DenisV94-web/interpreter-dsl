# История изменений

Формат — [Keep a Changelog](https://keepachangelog.com/ru/1.1.0/),
версионирование — [SemVer](https://semver.org/lang/ru/).

> Правило проекта: каждая новая возможность DSL попадает в этот файл
> и получает страницу (или раздел страницы) в `docs/` в том же коммите.

## [1.12.0] — 2026-08-26

### Добавлено

- **`set` в execute-actions** — декларативная запись/перезапись значений
  в контекст на этапе решений: `'set' => ['имя' => 'выражение']`.
  Выражения резолвятся по обычным правилам (`field:`, цепочки `|`,
  `{{ }}`, литералы, массивы с `field:`). `conditions` на действии
  учитываются — запись по условию. Позволяет дополнять и перезаписывать
  данные, подготовленные в `request`, и использовать их в следующих
  блоках и действиях.

## [1.11.0] — 2026-08-24

### Изменено

- **`ArrayTransformer::toSelectOptions`** получил декларативный механизм
  трансформаций: массив с `fn` + `args`, поддерживающий PHP-функции,
  методы классов (статические и нестатические), вложенные цепочки.
  Доступ к полям текущей строки — через префикс `item:ИМЯ_ПОЛЯ`
  (внутренний префикс ArrayTransformer, не DSL-префикс).
  Старый синтаксис «строка как имя поля» сохранён.

## [1.10.0] — 2026-08-23

### Добавлено

- **Независимые условия** — `'independent' => true` на блоке execute:
  условие проверяется независимо от цепочки if/elseif/else/switch
  и не прерывает её. Несколько независимых if подряд — срабатывают
  все истинные. `'else'` с `independent` не поддерживается (warning).
- **Вложенность execute** — action может содержать ключ
  `'execute' => [...]`: вложенные ветвления любой глубины
  (switch → case → if → execute → if → ...). Работает внутри
  if/elseif/else, внутри switch-case и в других вложенных execute.
  `conditions` на таком action учитываются; ошибка внутри
  вложенного блока прерывает весь execute.

## [1.9.0] — 2026-08-22

### Добавлено

- **`switch` в `execute`** — ветвление по значению выражения:
  `'check' => 'switch'`, `'expression' => 'field:...'`, `'cases' => [...]`
  с ключом `default`.
  - `expression` резолвится через Field (`field:`, `{{ }}`, литералы);
  - case проверяются в порядке конфига, сравнение слабое (`==`),
    без fall-through — выполняется ровно один case;
  - сработавший switch прерывает цепочку `if/elseif/else`;
    несработавший (без default) — передаёт управление следующему блоку.

### Совместимость

- Старые блоки `if` / `elseif` / `else` и блоки без `check`
  работают без изменений.

## [1.8.0] — 2026-08-21

### Добавлено

- **`ArrayFilter`** — отдельный сервис фильтрации списков объектов
  по фильтру в стиле Битрикс: `=`, `!`/`!=`, `>`, `<`, `>=`, `<=`,
  `%` (LIKE), `@` (IN), `!@` (NOT IN). Условия — AND, сравнение слабое
  (как в Битрикс), отсутствует поле → строка исключается.
  Вызов: `method: filter`, `class: \Api\Services\ArrayFilter::class`.
  Отдельные тест-сюита (`ArrayFilterTest`, 9 тестов) и страница
  документации `components/array-filter.md`.

---

## [1.7.0] — 2026-08-21

### Добавлено

- **dynamic-key-access** — доступ к значению поля по ключу, вычисленному
  на лету: `field:pr_hl[field:index_code]`. Работает во всех блоках
  (extra, query, mapping, execute, compose, curl, conditions) и в шаблонах:
  - внутри скобок: `field:` (включая цепочки `|` и вложенные скобки),
    литералы `'NEW_CAR'` / `"NEW_CAR"`, числа, голые имена как литералы;
  - комбинации с точечной нотацией: `field:a.b[field:k].name`,
    `field:m[field:r][field:c]`;
  - отсутствующий ключ или null-ключ → `null` (семантика всего DSL);
  - разделитель `|` учитывает глубину скобок — цепочки не ломаются
    на `field:a[field:x|field:y]`;
  - шаблоны: `{{field:arr[field:key]}}` и шорткат `{{arr[field:key]}}`.

## [1.6.0] — 2026-08-20

### Добавлено

- **`construct`** — декларативные аргументы конструктора при вызове
  нестатических методов (`method` + `class`):
  - элементы резолвятся по обычным правилам (`field:`, `{{ }}`, литералы,
    массивы с `field:`);
  - `['new' => Class, 'construct' => [...]]` — рекурсивное построение
    вложенных экземпляров, глубина не ограничена (порядок — изнутри наружу);
  - без `construct` поведение прежние (`new Class()`).
- **Диагностика конструктора**: если у конструктора есть обязательные
  параметры, а `construct` не указан — ошибка со списком параметров
  и подсказкой добавить `construct` (вместо cryptic ArgumentCountError).
- **`construct` в `error_context`**: при падении в лог попадает вся
  цепочка построения — класс и разрешённые аргументы каждого уровня.

## [1.5.0] — 2026-08-19

### Изменено

- **Запись лога разделена на две строки** согласно контракту корпоративного Logger:
  - строка запроса (`setRequest`) = `data` + `params` + `computed`
    — что успели собрать;
  - строка ответа (`setInfo`) = JSON из `buildLogResponse()`:
    сама ошибка с `error_context`, массив записей response,
    компактный `{"status":"SUCCESS"}`.
- Standalone Logger синхронизирован с корпоративным контрактом:
  `setInfo` хранит строку ответа; `setResponse` не используется.
- `error_context` пишется в ERROR-записи итераций (partial-режим).
- `max_log_size` применяется к каждой строке независимо:
  строка запроса — убрать `computed` → обрезать `data`;
  строка ответа-списка — сохранить первую, последнюю и ERROR-записи.
- `limitPayload` вызывается внутри `buildLogRequest()`/`buildLogResponse()` —
  прямые вызовы (тесты, отладка) возвращают уже ограниченный payload.

## [1.4.0] — 2026-08-19

### Добавлено

- **Error Context** — в `error.error_context` лога попадают `class`,
  `method` и `resolved_params` упавшего вызова. Теперь при TypeError
  в `getEntities($clientId, $clientType, $phone, $department)` сразу
  видно, какой аргумент был `null`. Применяется ко всем ошибкам методов,
  независимо от флага `logging`.
- **`max_log_size`** (дефолт 65 535 байт = MySQL TEXT) — предохранитель
  от переполнения highload-блока. При превышении лог деградирует
  в порядке: убрать `computed` → обрезать `data` → обрезать `response`.
  `status`, `error`, `error_context`, `params` не режутся никогда.
- **`log_response`** — флаг на эндпоинт. `null` (умолчание) = авто:
  итерационные пишут `response`, одиночные — нет. `true`/`false` —
  явное переопределение.
- **`transaction.snapshot_mode`** — `'all'` (умолчание, как раньше) |
  `'errors_only'` (только снимки упавших итераций) | `'first_last'`
  (первая + последняя + ошибки).

### Изменено

- `Exception\Execution` получил поле `errorContext` и параметр
  конструктора (обратно совместимо).
- `Context::setError` получил 5-й параметр `errorContext` (обратно совместимый).

## [1.3.2] — 2026-08-19

### Изменено

- **`logging: false` теперь всегда логирует ERROR-исходы.** Раньше флаг
  глушил лог при любом исходе, включая провал эндпоинта. Теперь
  `logging: false` глушит только чистый SUCCESS; в Logger **всегда** пишутся:
  - глобальные исключения (с 1.3.1);
  - ошибки контекста (`status: ERROR` — упавшие query/extra/execute);
  - ошибки итераций в режиме `partial` (даже при общем SUCCESS).

---

## [1.3.1] — 2026-08-19

### Изменено

- **`logging: false` больше не глушит критические ошибки.**
  Глобальные исключения (`ConfigException`, `ExecutionException`,
  неожиданный `Throwable`) пишутся в Logger **всегда**, независимо
  от флага. `logging: false` теперь глушит только штатные результаты
  и ошибки итераций.
- Убрано двойное логирование глобальных ошибок при `logging: true`
  (раньше писали и `logGlobalError`, и `logResult`).
- Вся запись в Logger идёт через единую точку `emitLog()` —
  тестируемо без реального Logger (`SpyInterpreter`).

## [1.2.0] — 2026-08-14

### Добавлено

- **`request_logic`** — произвольный порядок шагов блока `request`
  (например `['extra', 'curl', 'query']`). Без ключа действует
  дефолтный порядок `static → extra → query → curl` (обратная совместимость).
- **`response`-only действия** в `execute`: действие без `method` пишет
  запись в response (кейс «ошибка валидации с `task_id` без создания лида»).
- **`error_response`** — свои поля в ERROR-записи итерации
  (например `task_id` рядом с `status/message/config_path`).
- **`logging`** — флаг на действие: `false` отключает запись в логгер
  (`get_static` не пишет в `UF_REQUEST`, `create_lead` пишет).
- **`compose` с корневым выражением**: `'compose' => 'field:x'` возвращает
  объект без обёртки и без списка вокруг.
- **`extra`: рекурсивный резолв массивов** — `field:` внутри массивов-значений
  теперь разрешаются (`resolveParams`); ветки `check_true`/`check_false`
  принимают любые выражения, включая `method`.
- **Инфраструктура автономного репозитория**: standalone-автозагрузчик
  `src/autoload.php`, `tests/bootstrap.php`, standalone-версии
  `Logger`/`ResponseHandler`, двухрежимный раннер тестов
  (Bitrix / Standalone), папка `examples/` с нейтральными примерами,
  workflow авто-сборки документации.

### Изменено

- `static`-ключи исключены из `log.computed` (справочники не логируются,
  но доступны через `field:`).

## [1.1.0] — 2026-08-10

### Добавлено

- **Блок `static`** в `request`: сырые массивы-справочники и загрузка
  через `'Class::method'`.
- **Блок `curl`** в `request` и curl-действия в `execute`:
  GET/POST/PUT/DELETE/REST через `ICurlLogic`, `conditions`,
  `on_error`, шаблоны `{{params.*}}` в `url` и `headers`,
  статус `SKIPPED` при ложном условии.
- **`params`** — 4-й аргумент `Interpreter::run()`: доступны во всех блоках
  как `field:params.x` и `{{params.x}}`, переживают сброс итераций,
  видны в `buildLogRequest().params`.
- **Именованные списочные маппинги** в `mapping`: элементы с `source`
  и `mapping` (трансформация каждой строки списка), а также `source`
  без `mapping` (сырой список). Результаты пишутся в контекст под своими
  именами для `compose`.
- **`buildLogRequest()`**: единая структура лога — `data` + `params` +
  `computed` (всегда, включая SUCCESS) + `error` (при ошибках);
  в итерационном режиме — снимки `iteration_N` для всех итераций.
- **Снимки итераций** в `Context` (`snapshotIteration`,
  `recordIterationError`) для полного лога итерационных прогонов.
- Конвертация `endpoint`/`actionName` из snake_case в CamelCase
  для секции и метода логгера (`Interpreter:DesktopManager / CreateLead`).

## [1.0.0] — 2026-08-07

Первый релиз интерпретатора.

### Язык выражений (Field Resolver)

- `field:a.b.c` — точечная нотация любой глубины;
- цепочки альтернатив `field:a|field:b` — первое найденное значение;
- `func:empty`, `func:is_numeric` — структуры для условий;
- `method:Class->method` / `method:Class::method` — ссылки на методы
  с определением `static` через Reflection;
- `result` / `result:key` — результат последнего действия;
- шаблоны `{{field:x}}`, шорткаты `{{LEAD.NAME}}`, `null → ''` в тексте,
  одиночный плейсхолдер возвращает сырое значение с типом;
- литералы и неизвестные префиксы возвращаются как есть.

### Условия (Condition Resolver)

- равенства (нестрогие), отрицание `!field:x`,
- проверки `func:*` и `method:*`,
- `logic: AND|OR`, вложенные условия.

### Методы (Method Resolver)

- PHP-функции и методы классов (Reflection, static и instance);
- `element`: индекс, ключ, многоуровневый путь `'0.CODE'`;
- `mapping`-плейсхолдер в `params` (включая вложенные массивы);
- `on_error` — fallback при исключении или `false`;
- `change_values`: `class: 'self'` (метод на самом объекте),
  `name` (недеструктивная трансформация), PHP-функции, списки,
  null-источник без падения.

### Блоки

- `request`: `main` (post/get/request), `extra` (method / conditions +
  check_true/check_false, цепочки зависимостей), `query` (conditions,
  on_error), итерационный режим `array`;
- `mapping`: одиночный режим, вложенные массивы (множественные поля
  Битрикс) с рекурсивным резолвом;
- `execute`: `if / elseif / else`, `skip`, условия на отдельных actions,
  `response` с `result` / `result:key` / `field:`.

### Интерпретатор

- оркестрация `action_logic`, валидация конфига (`ConfigException`
  с путём в конфиге), `ExecutionException`;
- транзакции: `partial` (итерационная ошибка не прерывает цикл,
  запись `ERROR` в response[i]) и `all_or_nothing`;
- `ResponseHandler` с единой формой ответа
  `{status: {code, message}, data, global}`.

### Тестирование

- `TestLogger` (файловые логи с временными метками и JSON-данными);
- тест-классы: Field, Condition, Method, Request, Mapping, Execute,
  Interpreter; раннер `local/tests/run_interpreter_tests.php`.

## Как вести changelog

1. Новая возможность → секция `### Добавлено` будущей версии.
2. Изменение поведения → `### Изменено`, поломка совместимости →
   `### Изменено` + пометка **Breaking**.
3. Версии: `MAJOR` — ломает конфиги, `MINOR` — новая возможность,
   `PATCH` — исправления.
4. Дата — день слияния в `main`.
