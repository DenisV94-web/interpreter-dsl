# Шаблон страницы фичи

> **Правило проекта.** Фича без документации и тестов считается
> недоделанной. Коммит включает: код + тесты + changelog + страницу
> (или раздел страницы) в `docs/`.

---

## Процесс добавления фичи

1. **Код** — в соответствующем компоненте (Resolver/Executor/Interpreter).
2. **Тесты** — в подходящем тест-классе; прогон
   `php tests/run_interpreter_tests.php` → `Failed: 0`.
3. **Changelog** — запись в `docs/changelog.md` (версия по SemVer).
4. **Документация** — новая страница или раздел существующей.
5. **nav** — если страница новая, добавить ссылку в `mkdocs.yml`.
6. **Сборка** — после пуша GitHub Actions собирает с `--strict`:
   битые ссылки и отсутствующие файлы = ошибка.

---

## Куда класть страницу

| Что добавлено                | Где документировать          |
| ---------------------------- | ---------------------------- |
| Новая конструкция выражений  | `language/field.md`          |
| Новый синтаксис условий      | `language/conditions.md`     |
| Ключ/режим блока             | `executors/<блок>.md`        |
| Компонент, контекст, лог     | `components/*.md`            |
| Самостоятельная крупная фича | новая страница + пункт `nav` |

## Шаблон страницы

Скопируй и заполни. Блок ниже — сам markdown-шаблон
(вложенные примеры кода внутри него — в трёх кавычках):

````markdown
# Название фичи

> **Добавлено в версии X.Y.Z** (дата).
> Тесты: `НазваниеКласса::testИмяМетода` (N ассертов).

## Проблема

_Какую задачу решает? Что было невозможно или неудобно без фичи?
1–3 предложения, можно с мини-примером «как было»._

## Решение

_Краткое описание подхода: какой компонент изменён, какая семантика._

## Синтаксис

```php
'блок' => [
    'новый_ключ' => 'значение',
],
```

## Допустимые значения

| Ключ / значение | Тип | По умолчанию | Описание |
| --------------- | --- | ------------ | -------- |
| ...             | ... | ...          | ...      |

## Обратная совместимость

_Что происходит со старыми конфигами без нового ключа?
Обычно: «поведение не меняется»._

## Пример

```php
// минимальный рабочий конфиг с комментариями
```

Ожидаемый результат:

```json
{ "status": { "code": "SUCCESS" }, "data": [] }
```

## Тесты

- класс и метод;
- что проверяют (1–2 строки).

## См. также

- [Связанная страница](../...)
````

---

## Чек-лист готовности фичи

- [ ] код в компоненте;
- [ ] тесты добавлены в `runAll()` и зелёные;
- [ ] запись в `docs/changelog.md`;
- [ ] страница/раздел в `docs/` по шаблону;
- [ ] новая страница добавлена в `nav` (`mkdocs.yml`);
- [ ] пример в `examples/`, если фича меняет публичное поведение;
- [ ] после пуша — зелёный workflow «Build and Deploy Documentation».

---

## Добавление пункта nav

```yaml
nav:
  - Блоки конфигурации:
      - request: executors/request.md
      - новая_фича: executors/new-feature.md # ← новый пункт
```

После правки `nav` файл должен существовать, иначе `--strict`
сборка упадёт на этапе валидации ссылок.
